# 跨平台本地视频处理桌面软件设计

日期：2026-10-02。状态：书面方案已获用户确认，进入实施规划；实施计划与执行仍需确认。设计路径：Architectural。

依据：[原始需求](../../requirements/20261002-research/requirement.md)、[样本分析报告](../../requirements/20261002-research/analysis-report.md)。

## 1. 已确认的目标与证据边界

用户希望理解一个已知使用 FFmpeg 的 Windows 视频处理软件如何改变视频，并取得适合 Windows、macOS 的桌面落地方案。用户允许考虑 Tauri，已选择 Tauri + Rust + FFmpeg／ffprobe 外部进程路线。

本轮交付是样本分析报告和桌面设计。平台观察为抖音／小红书正常上传成功；用户已选择以技术分析与方案为验收，不要求本轮证明平台重复内容判定发生变化。

样本保持 720×1280、30 fps、2713 帧与视频时间轴，视频和音频载荷均改变；解码画面存在小幅差异，音频不仅改变采样率，还存在本次常规转码对照无法解释的变化。方案需支持这些处理类别，但不能把未定位的滤镜、原始命令或平台效果作为确定事实。

成功标准：处理链推断有证据和置信度；软件模块、参数、任务生命周期、失败行为与分发方式明确；实现者可以据此继续制定开发计划。桌面软件输出的本地校验结果不命名为“平台去重成功”。

## 2. 方案选择

| 路线 | 收益 | 成本与边界 | 决策 |
| --- | --- | --- | --- |
| Tauri 2 + Rust + FFmpeg／ffprobe sidecar | 参数、执行与校验可独立验证；媒体子进程与界面分离 | 需要为各目标平台准备二进制，并管理退出、取消及分发 | 采用 |
| Tauri 2 + Rust 直接调用 FFmpeg 库 | 更细地控制帧级处理和内存数据 | 增加 FFI、链接、构建及接口维护工作 | 当前需求不采用 |

Tauri 官方提供 `bundle.externalBin` 与 sidecar 运行方式，外部二进制按目标架构配置。这里据此选择外部进程集成；模块划分与生命周期是本项目的设计决定。[Tauri sidecar 文档](https://v2.tauri.app/develop/sidecar/)

界面建议使用 React + TypeScript + Vite，作为方案默认选型，尚不是用户单独指定的技术约束。视频处理、任务状态和参数校验放在 Rust 中；前端不依赖本机安装 Python、Node.js 或 FFmpeg。

## 3. 首版范围

首版围绕单文件本地处理：导入视频、查看探测信息、选择内置预设和输出目录、开始、查看进度、取消、查看结果及错误日志。任务运行期间再次点击开始不得创建重复任务；当前任务结束后可处理下一个文件。

输入契约为：MP4 中一个主视频轨，零或一个主音轨；8 bit SDR、恒定帧率、可输出 yuv420p 的偶数尺寸；音轨支持单声道或双声道。其他输入明确提示当前预设不支持，避免未经设计的格式和颜色转换。

输出为 MP4／H.264／AAC，保存独立文件，源文件保持只读。首版不包含完整剪辑时间轴、云处理、平台登录与自动上传；批量队列、GPU 加速、HDR 转换和自动更新作为后续单独设计的扩展。

### 3.1 预设策略

预设有稳定 ID、版本、适用条件、结构化参数、验证要求及证据状态。任务启动时冻结预设快照，避免界面修改影响正在执行的任务。

- **基础转换预设 `basic-transcode-v1`**：libx264 Main、veryfast、yuv420p，保持输入尺寸、恒定帧率和时间轴，禁用 B 帧，GOP 约十秒，禁用场景切换触发的额外关键帧。视频源码率可取得且有效时使用其目标码率，否则使用 CRF 18；两种模式互斥。不硬编码 H.264 level，由编码器根据输出规格生成。
- 音频使用 AAC、48000 Hz，保持支持的声道数；有效源音频码率按 64～128 kbit/s 限定，缺失时用 96 kbit/s。没有音轨就生成无音轨输出，不添加静音轨。视频与音频都不默认施加未知样本滤镜。
- **样本校准基线**：严格使用报告已运行的两条对照参数，作为研发实验，不作为通用输入预设。基础转换预设和实验基线不是同一个配置，二者各自记录完整参数。
- **样本研究预设**：轻微色调变化和额外音频处理是待校准候选，不纳入首版已验证预设。要把它开放给用户，必须先明确参数、适用条件，记录与原视频、目标样本和无滤镜基线的比较，再更新证据状态。

基础预设保持视频帧和时间轴，不要求其他输入的关键帧表保持不变。保留 SDR 颜色范围及可取得的颜色标记，不用写入标签替代实际颜色转换；来源颜色信息无法确认时提示该信息缺失，不能宣称完成了颜色一致性验证。

这意味着首版可以完成可追溯的本地转换；**与原软件完整处理效果的近似匹配仍需要独立的样本校准阶段**。它没有被基础预设悄悄替代，也不作为首版已经完成的能力。

容器元数据允许保留或显式改写 title／comment；默认保留输入信息并写入本工具真实的处理标识，不伪装原软件的编码器版本。日志记录模式、实际值和任务 ID；这些字段用于可追溯性，不赋予平台效果含义。

## 4. 模块与接口

| 单元 | 责任及使用方式 | 依赖 |
| --- | --- | --- |
| 媒体探测 | 根据用户选择的本地文件返回 `MediaInfo`；识别预设是否适用 | ffprobe、文件访问 |
| 预设与参数 | 根据 `MediaInfo` 和预设版本生成不可变 `ProcessingPlan`，包括参数列表及验证策略 | 内置预设；不启动媒体进程 |
| 任务执行 | 根据计划启动 FFmpeg，解析进度、管理取消，输出 `JobSnapshot` 和受限长度日志 | sidecar、任务状态、临时输出 |
| 输出校验与保存 | 根据计划检查临时媒体，通过后保存为独立正式文件，返回 `ValidationResult` | ffprobe、FFmpeg 解码验证、文件系统 |

前端只通过受控 Tauri commands 请求：探测输入、读取预设、开始任务、读取任务快照、取消任务、定位已生成结果。Rust 校验文件和参数，使用程序名加参数列表运行 sidecar，不拼接 shell 命令字符串。

前端不能提交任意 FFmpeg 参数、滤镜文本或可执行路径，也不获得通用 shell 执行权限。应用加载本地打包界面；日志可以查看实际参数供诊断，但普通处理流程不要求用户理解 FFmpeg 选项。

核心数据约定：

- `MediaInfo`：文件身份、容器、轨道、尺寸、像素格式、颜色信息、帧率、时间轴、声道及采样率；不可用字段明确为缺失，不能把未知码率视为零码率。
- `ProcessingPlan`：任务 ID、输入身份、预设 ID／版本、冻结参数、实际编码器、输出目录与临时文件、预计时长、验证条件。
- `JobSnapshot`：任务 ID、单调递增状态版本、当前阶段、媒体处理进度、开始和结束时间、结果或结构化错误。
- `ValidationResult`：探测与完整解码结果、规格和时长检查、输入及输出哈希、实际保存路径。哈希变化仅表示文件不同。

Rust 持有权威状态；事件是通知，重新连接界面通过任务快照恢复显示，旧事件不得覆盖更高版本状态。

不能仅凭 `nb_frames`、平均帧率或容器总时长就断言输入帧数、CFR 和音视频时长。必要信息缺失时追加读帧及时间戳探测；仍无法确认则拒绝当前预设，避免跳过其输出验收。

## 5. 数据流与任务生命周期

```text
导入 → 探测与适用性检查 → 冻结处理计划 → 临时输出
     → 探测与完整解码校验 → 保存正式文件 → 显示完成
```

状态依次为 `probing → preparing → running → validating → committing → succeeded`，中间可进入 `failed`；提交前各阶段均可经 `canceling → canceled` 结束。终态不可再被延迟到达的进度或退出事件修改。

首版同一时刻仅处理一个任务。探测也在后台运行；FFmpeg 的 stdout 解析机器可读进度，stderr 保存受限日志。使用 `-progress pipe:1`、`-nostats`，按计划时长计算运行阶段进度，展示阶段名称；只有校验和保存都成功才显示整体完成。[FFmpeg progress 文档](https://ffmpeg.org/ffmpeg.html)

临时文件放在所选输出目录的任务专属子目录中，使用 `.mp4` 扩展名或明确指定 muxer。正式命名为 `<源名称>_processed_<任务ID>.mp4`；临时和正式文件均不能与输入路径或已有结果冲突。

同目录保存便于原子发布。最终保存采用拒绝覆盖既有目标的操作；若平台所用接口不能同时满足原子发布和拒绝覆盖，则先独占保留目标名称再使用匹配的保存策略，不依赖“检查不存在，再普通 rename”的竞态窗口。

输入在计划建立时记录身份、大小和修改时间，输出校验前再次检查；发生变化时失败，不把混合输入结果当作成功。任务日志记录工具版本、参数、耗时、输出和校验结论；日志默认只存本地。

## 6. 取消、失败与输出校验

### 6.1 取消和异常处理

取消以 Rust 状态为准：停止继续进入下一阶段，通知当前媒体子进程退出，等待最多三秒，仍存活则终止并回收；完成回收后才删除临时文件、进入 canceled。探测、处理和校验进程都归同一任务管理。

临时文件清理失败时保留自有未完成标记，报告清理问题并在重启时继续识别；不能把遗留媒体当作成功输出，也不能声称已经清理完毕。

进入 `committing` 前，在同一状态锁下确认未收到取消；保存与终态变更串行执行。已经进入提交或完成阶段的取消返回当前状态，不出现“显示已取消但正式文件稍后生成”。关闭应用时沿用取消与回收流程。

启动时只识别应用自有命名及标记的临时任务目录；异常退出留下的媒体标记为未完成，经清理后才能复用任务资源。应用不得根据通配符删除用户目录中的其他文件。

错误区分：不支持的输入、损坏媒体、sidecar 不可用、输出无权限或空间不足、媒体进程退出、校验失败、保存冲突。向用户显示具体原因和日志入口，失败后可以重新开始；不自动重试参数错误或磁盘写入错误。

### 6.2 输出校验

FFmpeg 正常退出只是必要条件。输出还必须非空、可探测、可完整解码，并符合计划中的轨道、分辨率、帧率、像素格式与音频规格。解码错误使校验失败。

保持时间轴的基础预设要求输出视频帧数与输入一致，视频时长偏差不超过一个输入帧。输出音轨存在性及声道数与计划一致，AAC 为 48 kHz；音轨时长相对输入的允许差值为 `max(一个输入视频帧时长, 50 ms)`，以容纳编码延迟和尾部填充。此时长检查不等同于完整听觉同步验证。

哈希用于输入身份和结果追溯，不以“输出哈希不同”作为画质、原创性或平台识别的验收。全片 SSIM／PSNR 属于研发校准检查，不默认在每个普通任务上计算；发布预设前需要在校准片上核对画面与音频，避免把损坏或明显失真当作有效变化。

## 7. 跨平台分发

首版目标为 Windows x64、macOS Apple Silicon 和 Intel，分别构建、分别验证。最低系统版本以锁定的 Tauri、WebView 和 FFmpeg 构建实际通过的发行矩阵公布，不据本机环境宣称其他版本已支持。

FFmpeg 与 ffprobe 作为 sidecar 打包，同一发行版本记录二者版本、构建配置、二进制校验和和许可证。`bundle.externalBin` 指向 `binaries/ffmpeg`、`binaries/ffprobe`，构建资源按平台采用对应 target triple：

| 平台 | 资源后缀 | 分发形式 |
| --- | --- | --- |
| Windows x64 | `-x86_64-pc-windows-msvc.exe` | NSIS 安装包；按需增加 MSI |
| macOS Apple Silicon | `-aarch64-apple-darwin` | `.app` + DMG |
| macOS Intel | `-x86_64-apple-darwin` | `.app` + DMG |

Windows 安装器检查 WebView2；普通安装可使用下载 bootstrapper，离线分发选择 `offlineInstaller`，相应增加安装包体积。处理过程仍只使用本地文件。[Tauri Windows 安装文档](https://v2.tauri.app/distribute/windows-installer/)

macOS 分别检查主应用与 sidecar 的签名、执行权限及架构，发布包经过代码签名和公证，再在干净机器测试 Finder 启动与实际转码。Windows 发布包也检查签名与安装后启动；构建成功不能替代实际安装验证。[Tauri macOS 分发](https://v2.tauri.app/distribute/macos-application-bundle/)、[代码签名](https://v2.tauri.app/distribute/sign/macos/)

本次研究机的 FFmpeg 启用了 GPL 组件，包括 libx264。发行包必须依据所选构建提供许可证、说明和对应源码等材料；sidecar 进程隔离不自动免除分发义务。本设计不据此推断桌面应用本身必须采用某一种许可证。[FFmpeg 许可说明](https://ffmpeg.org/legal.html)

## 8. 验证与交付标准

### 本轮文档

1. 原视频和编辑后视频的实测差异可追溯到输入哈希及测量方法。
2. 已测事实、处理链推断和未知项明确区分；含无滤镜视频及普通 AAC 转码对照。
3. Desktop 模块、接口、预设适用范围、失败行为、分发方式及能力边界一致。
4. 原视频和编辑后视频的哈希与分析开始时一致。

### 后续软件验收

| 检查 | 预期结果 |
| --- | --- |
| 选定样本，执行基础转换 | 独立输出、规格和时长符合计划、完整解码通过 |
| 中文、空格及含引号路径 | 参数正确传递，文件可读写，未触发 shell 解释 |
| 重复点击开始 | 同一输入的当前任务不会被重复启动 |
| 无音轨输入 | 成功输出无音轨视频，校验策略相应适配 |
| 损坏、HDR、变帧率或不支持的多轨输入 | 明确拒绝或校验失败，给出具体原因 |
| 缺失 sidecar、无写入权限、磁盘不足 | failed，无正式成功产物，错误可定位 |
| 处理／校验中取消、关闭应用 | 子进程回收，临时文件清理，不再生成正式结果 |
| 取消与结束事件同时到达 | 仅一个合法终态，界面与文件结果一致 |
| 正式输出重名或输入处理中变化 | 拒绝覆盖／校验失败，保留用户原有文件 |
| 异常退出后重启 | 识别本工具残留，未完成文件不显示为成功 |
| 三个平台安装包 | 在无开发工具环境完成安装、启动、处理和取消 |

参数生成、状态转换及终态竞争使用针对性单元测试；真实 sidecar、解码校验和安装包使用集成检查。测试依据上表中的行为，不只断言参数字符串或界面元素存在。

## 9. 推进顺序与剩余研究

1. 用户审核本书面设计，修正目标或边界后进入实现规划。
2. 用已记录基线建立媒体处理与校验接口；单独研究色调及音频候选，避免基础转换被标为完整样本复现。
3. 完成单文件 Tauri 应用和任务闭环，再验证三个平台安装包。
4. 只有候选处理链取得明确参数和校准记录，才将它作为新的预设发布。若没有足够证据，保留未知状态而不是虚构滤镜。

性能、安装包大小和样本匹配程度需要后续实测，本文件不提供未测的数字承诺。批量、多平台上传或完整剪辑器均需另行界定范围。

书面方案获批后，下一步使用 `superpowers:writing-plans` 编写实施计划；方案审核本身不代表批准尚未存在的实施计划或执行方式。
